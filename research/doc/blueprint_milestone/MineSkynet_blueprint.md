# MineSkynet 연구 청사진

최종 갱신: 2026-10-24

기준 시스템: VillagerAgent(VA)와 VillagerBench. 단계별 완료 조건은 [연구 마일스톤](research_milestone.md), 현재 위치는 [인덱스](milestone_index.md), 날짜별 근거는 [리포트 로그](../human_report/report_log.md)를 따른다.

## 1. 연구 질문과 피벗

> VA에서 고수준 계획은 생성형 모델에 남겨 두고 제한된 행동 선택과 작업 배정을 경량 결정 정책으로 분리할 때, 과제 성능·실행 시간·추론 비용은 어떻게 달라지는가? 관찰된 득실은 어느 단계에서 발생하는가?

기존의 **에이전트 수 증가에 따른 모든 협업 효율 저하 원인 규명**은 필수 목표에서 내린다. Construction Task0·64의 성능 변화는 배경이며, 새 정책을 도입하기 전에 자원 경쟁·DAG 병목·서비스 지연을 모두 규명할 필요는 없다. 개선 부재, 완료율 저하, 비용과 성능의 상충도 유효한 결과다.

[S1-MAS](https://arxiv.org/abs/2610.08155)의 제한된 조정 결정 분리와 [Jev-LiteMAS](https://arxiv.org/abs/2610.21411)의 결정–생성 역할 구분을 참고한다. 두 논문의 다른 환경에서의 성능을 VA의 검증된 효과로 옮겨 쓰지 않는다. 특정 JEV 모델 채택·가용성은 미확정이다. 여기서 **결정형**은 유효한 후보 중 선택하는 정책 계열이며, 단순 규칙·경량 모델·JEV류 모델을 구분한다.

## 2. 비교 축과 보존할 경계

TD/Task Manager의 부분 DAG 계획, SM/Data Manager의 상태·이력, Minecraft 실행 API와 VillagerBench judger는 출발 기준으로 보존한다. 현재 SM은 LLM 요약·환경 질의도 수행하므로 비LLM 모듈이라고 단정하지 않는다. BA의 reflection과 환경 judger 점수도 구분한다. 논문–코드 차이는 [기능 대응표](../architecture_understand/VA_code_paper_map.md)를 따른다.

| 조건 | AC 작업 배정 | BA/Minecraft Agent의 다음 행동 선택 | 실험 역할 |
| --- | --- | --- | --- |
| G/G | 현행 생성형 경로 | 현행 생성형 경로 | 기준선 |
| G/D | 현행 생성형 경로 | 결정형 경로 | **1차:** 행동 선택의 득실 |
| D/G | 결정형 경로 | 현행 생성형 경로 | **2차:** 배정 선택의 득실 |
| D/D | 결정형 경로 | 결정형 경로 | 단독 효과 확인 후 결합 효과 |

`G/D`는 **BA 전체 교체가 아니다.** 첫 교체 대상은 배정된 작업 아래의 *다음 행동 선택*이다. 지시 해석, 후보·인자 생성, 실패 설명과 reflection 중 생성형 추론이 필요한 부분은 별도 경계로 남길 수 있다. 도구 이름뿐 아니라 좌표·아이템·대상 등 실행 가능한 인자를 처리해야 실제 행동 정책이다.

AC와 BA에는 만능 API 하나가 아닌 두 정책 계약을 둔다. `AssignmentPolicy`는 ready 작업·적격/가용 agent·상태를 받아 유효한 배정 또는 보류를 반환한다. `ActionPolicy`는 작업 지시·관측·허용 행동 집합을 받아 다음 도구와 필요한 인자를 반환한다. 생성형/결정형 구현이 각 계약을 따르며, 후보 구성·제약 검증·실행·채점은 공통으로 둔다. 무효 출력과 fallback은 숨기지 않는다. **이는 설계 목표이며 아직 구현된 기능이 아니다.**

## 3. 검증할 주장과 해석 한계

1. **BA 축:** 행동당 결정 지연·호출/토큰 비용이 감소하는가? 유효 행동률과 과제 완료 성능은 유지되는가? 빠른 결정도 인자 오류·재시도로 전체 시간을 늘릴 수 있다.
2. **AC 축:** 실제 LLM 배정 기회에서 적격 Worker를 더 적은 비용으로 고르는가? 현재 TD가 후보를 먼저 제한하며 AC에는 직접 배정도 있다. 호출 빈도와 의미 있는 대안의 존재를 먼저 확인한다.
3. **결합:** 두 변경의 효과는 독립적인가, 서로 증폭·상쇄하는가? 단일 축 결과가 안정된 뒤 2×2 전체를 비교한다.

정책 교체 실험이 식별하는 것은 우선 **정책 전체의 효과**다. 단계별 로그 없이 모델 속도, 판단 품질, API 대기, Minecraft 실행 실패 중 하나를 원인으로 단정하지 않는다. 에이전트 수와 게임 내 능력 이질성은 처음부터 함께 바꾸지 않는다.

## 4. Benchmark와 지표

VillagerBench의 소수 과제를 먼저 고른다. Construction은 기존 실행·시각적 판정이 가능한 **기준 과제**다. Farm-to-Table은 병렬 재료 획득과 선행 조리·제작 때문에 **주력 후보**다. 쉬운 Cake 설정에서 경로를 확인하고, 실제 TD·AC 선택지와 행동 후보가 나타나는 과제로 좁힌다. Escape Room은 순차·동시 행동의 **후속 후보**다. 탈출 생성기는 에이전트 수를 입력받으므로 인원 변경 시 과제 자체가 달라지지 않는지 확인해야 한다. TickingCollabBench 등의 외부 benchmark 이식은 VA 내 비교가 성립한 뒤 별도 결정한다.

현재 실행 진입점의 Controller 주도 배정은 full Controller·Construction·동질 에이전트에 한정된다. 따라서 요리의 **BA 축**과 요리의 **AC 축**은 구현 준비 정도가 다르다. Farm-to-Table에서 AC 비교가 바로 된다고 전제하지 않고, 동일 과제·동일 제약의 정책 대조가 가능해질 때만 경로를 확장한다.

| 결과 층위 | 최소 관측값 |
| --- | --- |
| 과제 성능 | judger 완료율·성공/부분완료, 총 wall-clock 시간, 실패·복구 |
| 의사결정 | AC 직접/LLM 배정, BA 후보·선택·인자 유효성, 정책별 지연·fallback |
| 자원·비용 | 역할별 호출 수·토큰·금액, 외부/로컬 추론 시간, actor 유휴·활동 |
| 시나리오 고유 지표 | Construction의 VHR, Cooking의 ACR 등 해당 지표만 적용; B·E의 정의·분모도 명시 |

**결정 지연 감소**와 **과제 완수 시간 감소**를 별도로 판정한다. 외부 API 비용을 로컬 추론 비용으로 옮기는 경우 측정 경계를 밝힌다. 반복 횟수, 주 지표, 허용 성능 손실과 비용 예산은 본 비교 전에 고정한다.

## 5. 실행 순서와 범위 경계

BA의 관측→후보·인자→선택→실행→피드백 경계를 먼저 확인하고, 공통 계약을 통과하는 G/G 기준선을 재현한 다음 G/D를 비교한다. AC는 LLM 배정의 기회와 후보 제약을 확인한 뒤 D/G로 넘어간다. D/D와 과제·에이전트 수 확장은 마지막이다. 통과·중단 조건은 [연구 마일스톤](research_milestone.md)에 둔다.

이기종 물리 장치 할당, Odyssey 이식, 모든 VA 디버깅, 새 benchmark 구축, 전체 DAG 최적화, 기존 scaling 저하의 포괄적 인과분해는 필수 완료 조건이 아니다. 변경 전후 실행을 같은 조건의 반복으로 합치지 않는다.
