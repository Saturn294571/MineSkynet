## 목표와 증거 원칙

> VA의 제한된 행동 선택(BA)과 작업 배정(AC)을 각각 결정형 정책으로 분리했을 때, 동일 과제에서 완료 성능을 유지하며 시간·비용을 줄일 수 있는가? 어느 결정 단계의 차이가 실제 이득 또는 손실로 이어지는가?

**BA 행동 선택을 1차 축, AC 작업 배정을 2차 축**으로 둔다. 두 축의 생성형(G)/결정형(D) 정책이 각자의 공통 계약을 따르게 하고, G/G → G/D → D/G → D/D 순으로 확대한다. 처음부터 특정 JEV 모델의 우위, 실시간성 향상, 에이전트 수 증가 문제의 해결을 전제하지 않는다. 오프라인 계약 검사는 Minecraft 완주 증거가 아니다.

## 0. 이전 VA 실행 기반 `[x]`

- [x] 원본 `controller.py`로 작은 Construction 실행 경로를 확인했다.
- [x] 평지·Peaceful 조건의 Task20·3인에서 actor 출력·파서·피드백 문제를 다룬 후 한 실행이 12/12 블록·`complete task`로 끝났다. [점수](../../../result/gemini-3.8-flash_construction_task20_3p_controller_llm_flat_20261007_trial2_feedback1024/score.json)
- [x] [Task25 TD/AC 프로브](../../../result/td_ac_probe_task25_20261007/probe.json)는 합성 환경의 첫 라운드에서 3 node·0 edge와 유효 배정 3개를 확인했다.

이 근거는 VA의 실행·분리 검사이지 새 정책 성능, agent 수 효과 또는 원 논문 전체 benchmark의 재현이 아니다. 이전의 병목 전면 귀속 계획은 별도 역사적 맥락이며 아래의 선행 통과 조건이 아니다. 실행·진단 세부 기록은 [리포트 로그](../human_report/report_log.md)에 둔다.

## 1. BA 행동 선택의 교체 가능성 판정 `[ ]`

- [ ] [BaseAgent](../../../pipeline/agent.py)에서 작업 수신·reflection과 실제 행동 선택을 분리해 설명한다. [Minecraft Agent](../../../env/minecraft_client.py)의 관측→ReAct 추론→도구·인자→실행→피드백 경계를 추적한다.
- [ ] 두 정책이 받을 동일한 작업·관측·허용 행동 집합을 정의한다. 행동 **종류뿐 아니라 좌표·아이템·대상 등의 인자**를 생성 또는 제한할 책임을 명시한다.
- [ ] `ActionPolicy`의 입력·출력 스키마, 유효성 검사, 무효 선택·타임아웃·fallback 계약을 정한다. 기존 생성형 행동과 결정형 행동 모두 같은 외부 계약을 따르되 결과를 조용히 보정하지 않는다.
- [ ] 일부 작업에 열린 자연어 추론이나 새 인자 생성이 불가피하면 생성형 역할로 남기거나 첫 과제·행동 집합을 더 좁힌다.

**통과 기준:** 같은 상태에서 두 정책이 선택할 수 있는 유효 행동과 실행 인자를 명시하고, 현행 도구 실행·결과 판정을 공유할 수 있음을 정적 분석과 작은 fixture로 보인다. 이것이 안 되면 결정 모델 구현을 시작하지 않는다.

## 2. Benchmark 선별·G/G 기준선 `[ ]`

- [ ] Construction의 검증된 작은 과제를 기준 경로로 유지하고, Farm-to-Table의 쉬운 Cake 과제를 BA 1차 주력 후보로 조사한다. 두 과제 모두 실제 정책 선택 기회·도구 행동·실패 유형을 본 뒤 선정한다. Escape Room은 동시 행동·생성기 제약을 확인한 후속 후보로 둔다.
- [ ] 새 공통 계약을 통과시켜도 G/G 현행 생성형 경로의 과제 성능·행동 종류·오류가 납득 가능한 범위에서 재현되는지 확인한다. 계약 도입 전후의 조건·차이는 그대로 기록한다.
- [ ] 실행 단위로 코드 commit, 과제·agent 수, 모델·프롬프트, 월드·난이도·스폰, 도구 집합, Controller 경로, judger 설정을 보존한다. 기준선과 대조군은 동일한 종료 조건·예산을 사용한다.
- [ ] 주 지표, 반복 횟수, 성공 허용 오차와 비용 상한을 대조 실험 전에 정한다.

**통과 기준:** 선택 과제에서 actor 포함 G/G 실행과 환경 judger 결과가 보존되고, 동일 계약이 기준선의 동작을 의도치 않게 바꾸지 않았음을 확인한다. Task25처럼 actor 없는 프로브만으로 통과하지 않는다.

## 3. G/D: BA 단일 축 비교 `[ ]`

- [ ] 제한된 행동 선택을 하는 결정형 정책 하나를 구현·연결한다. 단순 규칙을 진단용 비교군으로 사용할 수 있으나 특정 JEV 모델 사용은 사전 전제가 아니다. 모델 공급자·로컬 추론 비용을 별도로 적는다.
- [ ] TD·AC·SM, 에이전트 수, 월드, 작업 목표, 행동 도구와 검증기를 고정하고 BA 정책만 바꾼다. 기존 생성형 기능이 남는 구간과 fallback 발생을 표시한다.
- [ ] 행동당 선택 지연·유효 행동률·인자 오류·재시도, 역할별 호출/토큰/비용과 전체 완료율·wall-clock 시간·judger 점수를 함께 비교한다.
- [ ] 반복 결과의 변동성과 실패 사례를 제시한다. 결정 지연 단축이 과제 시간 단축으로 이어지지 않으면 재시도·행동 품질·환경 대기를 구분한다.

**통과 기준:** G/G와 G/D의 성능–시간–비용 득실 및 남은 혼입 요인을 원시 로그로 설명한다. 성능 향상 자체는 통과 조건이 아니다. 하나의 정책 차이로 기존 VA 전반의 scaling 병목 원인을 단정하지 않는다.

## 4. D/G: AC 단일 축 비교 `[ ]`

- [ ] [Task Manager](../../../pipeline/task_manager.py)의 후보 설정과 [Controller](../../../pipeline/controller.py)의 직접 배정·LLM 배정을 분리 계측한다. 유효한 대안이 둘 이상인 결정 시점이 충분한지 확인한다.
- [ ] `AssignmentPolicy`의 ready 작업·후보·가용성·필요 인원 입력과 배정/보류 출력을 정의한다. 선행조건·중복·인원·가용성 검증은 양쪽에서 동일하게 수행한다.
- [ ] BA는 G로 고정한 채 G/G와 D/G를 비교한다. 현재 Controller 주도 배정은 full Controller·Construction·동질 agent에 한정되므로 Farm-to-Table로 확장한다면 그 호환성 변경부터 별도 검증한다.
- [ ] 직접 배정으로 정책 선택이 없었던 경우를 모델 성과에 합산하지 않는다. 배정 지연·유효성·재할당·전체 과제 성능·비용을 함께 보고한다.

**통과 기준:** 실제 배정 선택지가 있는 동일 조건에서 AC 정책 단독 효과를 추정한다. 대부분 직접 배정이거나 선택 결과가 사실상 같으면 이를 미관찰로 보고, AC 축의 확대를 보류할 수 있다.

## 5. D/D 결합·일반화 결정 `[ ]`

BA와 AC의 단일 축 결과가 해석 가능할 때만 네 조건(G/G, G/D, D/G, D/D)을 같은 과제에서 반복 비교한다. 결합 효과와 상호작용을 구분하고, 이후에만 다른 VillagerBench 과제·에이전트 수·게임 내 능력 이질성·외부 benchmark 확장을 선택한다. Escape Room은 인원에 따라 생성된 과제 내용이 바뀔 수 있으므로 같은 과제 비교 가능성을 확인한다.

**최종 산출물:** 재현 조건과 원시 로그가 연결된 네 정책 조건의 과제 성능, 지연, 호출·비용, 실패·fallback 비교 및 효과가 발생한 단계의 설명. 결합 실험이 성립하지 않으면 단일 축의 해석 가능한 결과와 그 한계를 최종 결과로 남긴다.

## 비목표와 중단 경계

이기종 물리 장치 라우팅, Odyssey 이식, 전체 DAG 최적화, 새 benchmark 제작, VA 모든 결함 수리, 에이전트 수 증가의 모든 원인 인과분해는 필수 단계가 아니다. 실행 환경·채점·모델·프롬프트가 달라지면 같은 조건의 반복으로 합치지 않는다. 기존 `result/`와 로그를 보존하고, 실패나 미관찰도 기록한다.
