# VillagerAgent 연구에 OR을 적용할 가능성

제시하신 랩미팅 문서와 원본 논문을 함께 검토하면, **현재 연구는 OR(Operations Research)의 자원 할당, 스케줄링, 대기행렬이론과 상당히 직접적으로 연결됩니다.**

특히 중요한 점은 VillagerAgent가 이미 DAG 기반 작업 관리를 도입했다는 사실입니다. 따라서 연구 방향을 단순히 '그래프 스케줄링 기법을 적용하자'로 설정하면 원본 연구와 차별성이 부족할 수 있습니다.

반면 다음과 같이 접근한다면 이야기가 달라집니다.

> **VillagerAgent에서 에이전트 수가 증가할 때 나타나는 효율 저하를 자원 경쟁과 관리 오버헤드로 구분하고, 각 요인이 확장성에 미치는 영향을 실증적으로 규명한다.**

이는 새로운 스케줄링 알고리즘의 개발에 앞서, 기존 시스템의 성능 저하 원인을 식별하는 연구입니다.

또한 지금 작성하신 두 가설과 잘 부합합니다.

## 1. 원본 VillagerAgent 논문과 연구 질문의 관계

참고 논문은 다음과 같습니다.

**Dong et al. (2024), *VillagerAgent: A Graph-Based Multi-Agent Framework for Coordinating Complex Task Dependencies in Minecraft*.**

- 발표: Findings of ACL 2024
- [논문 원문](https://aclanthology.org/2024.findings-acl.964/)
- [GitHub 저장소](https://github.com/cnsdqd-dyb/VillagerAgent-Minecraft-multiagent-framework)

논문은 VillagerBench라는 Minecraft 기반 다중 에이전트 벤치마크와 VillagerAgent 프레임워크를 제안합니다.

프레임워크는 크게 세 구성요소를 갖습니다.

| 구성요소 | 역할 | OR 관점의 해석 |
| --- | --- | --- |
| Task Decomposer (TD) | 작업 분해 및 DAG 생성 | 선후관계 제약을 갖는 작업 모델링 |
| Agent Controller (AC) | 에이전트별 작업 할당 | 자원 할당 및 스케줄링 |
| State Manager (SM) | 환경 및 에이전트 상태 관리 | 상태 관측 및 정보 갱신 |

즉, VillagerAgent는 이미 상당 부분 OR 문제에 가까운 구조를 가지고 있습니다.

원본 논문은 이러한 구조가 복잡한 작업 의존성을 처리하고 에이전트 간 협업을 개선하는 데 효과적임을 보여주었습니다. [ACL Anthology](https://aclanthology.org/2024.findings-acl.964/?utm_source=chatgpt.com)

여기서 사용자님의 연구 질문을 다시 살펴보겠습니다.

> 에이전트 수에 대해, 작업효율/에이전트당 효율의 저하의 원인은 무엇인가?

원본 연구가 주로 **복잡한 작업을 여러 에이전트가 어떻게 협력하여 수행할 것인가**에 초점을 맞춘다면, 지금의 연구 질문은 **에이전트 수를 늘렸을 때 협업 시스템의 성능이 왜 저하되는가**에 초점을 맞춥니다.

두 연구는 관련되어 있지만 구분되는 질문입니다.

다만 원본 논문에서도 확장성과 효율성을 다루고 있으므로, 실제 선행연구 대비 차별성은 기존 실험과 부록에서 측정한 지표 및 비교 조건을 확인한 뒤 확정해야 합니다.

## 2. 가설 1: 에이전트 간 자원 경쟁이 효율 저하를 일으킨다

이 가설은 OS의 공유자원 관리뿐 아니라 OR의 자원제약 스케줄링과 직접 연결됩니다.

여기서는 자원을 두 종류로 구분하는 것이 좋겠습니다.

### A. Minecraft 환경 내부의 자원

예를 들어 다음과 같습니다.

- 동일한 작업 공간
- 제한된 아이템과 도구
- 특정 블록이나 시설에 대한 접근
- 에이전트 사이의 이동 경로 충돌
- 다른 작업이 완료되어야 사용할 수 있는 중간 산출물

에이전트가 많아지면 전체 작업 처리 능력이 증가할 수 있지만, 동시에 공유자원에 대한 경쟁도 증가할 수 있습니다.

예컨대 다수의 에이전트가 하나의 작업대에 접근해야 한다면, 추가적인 에이전트가 반드시 성능 향상으로 이어지지는 않습니다.

이 문제는 **Resource-Constrained Project Scheduling Problem(RCPSP)**과 연결할 수 있습니다.

단, 일반적인 RCPSP에서는 작업, 자원 요구량, 선후관계, 자원 용량을 명시적으로 정의합니다.

Minecraft의 모든 작업을 곧바로 RCPSP로 모델링할 수 있는 것은 아닙니다. 특히 공간 충돌이나 이동 경로의 상호작용은 별도의 공간·시간 제약 모델이 필요할 수 있습니다.

### B. 시스템 및 API 자원

두 번째는 Minecraft 환경 자체가 아니라 에이전트를 실행하는 컴퓨팅 시스템의 자원입니다.

예를 들어 다음과 같습니다.

- LLM API의 동시 요청 처리 능력
- API 응답 지연
- 요청 속도 제한
- Minecraft 서버의 처리 성능
- 에이전트 간 공유 상태 갱신
- 네트워크 및 서버의 대기시간

이 경우 에이전트 수에 따른 효율 저하는 게임 내부의 자원 경쟁 때문이 아닐 수도 있습니다.

예를 들어 8개 에이전트가 동일한 작업을 공유하지 않더라도, API 호출이 집중되어 응답이 지연된다면 전체 작업시간이 증가할 수 있습니다.

따라서 두 유형을 구분하지 않으면 실험 결과에 대한 인과적 해석이 어려워집니다.

**가설 1은 Minecraft 환경의 자원 경쟁과 컴퓨팅 인프라의 자원 경쟁을 구분해서 측정할 필요가 있습니다.**

## 3. 가설 2: LLM의 관리복잡도 증가가 효율 저하를 일으킨다

이 가설은 OR의 스케줄링뿐 아니라 CS의 알고리즘 복잡도, 분산시스템, 대기행렬이론과 연결할 수 있습니다.

특히 원본 논문에 중요한 근거가 있습니다.

원본 논문의 Section 4.2에서는 에이전트 수가 일정 수준을 넘으면 성능이 저하되며, 가능한 원인으로 자원 경쟁과 LLM의 관리복잡도 증가를 언급합니다.

또한 Limitations에서는 8개 에이전트까지 확장하는 과정에서 나타난 성능 저하를 설명하며 컨텍스트 길이 증가와 작업 그래프 생성의 복잡성을 지적합니다. [ACL Anthology](https://aclanthology.org/2024.findings-acl.964.pdf?utm_source=chatgpt.com)

여기서 중요한 것은 **원본 저자들도 이 원인들을 실험적으로 분리하여 입증했다기보다 가능한 설명으로 제시하고 있다는 점**입니다.

바로 이 지점이 현재 연구가 기여할 수 있는 부분입니다.

### 3.1. 관리복잡도를 세 가지로 분해할 수 있습니다

| 구분 | 의미 | 관측 가능한 지표 |
| --- | --- | --- |
| 계산 오버헤드 | LLM 추론에 필요한 처리량 증가 | 토큰 수, API 응답시간, 추론시간 |
| 스케줄링 복잡도 | 작업과 에이전트의 매칭이 어려워짐 | 할당 실패율, 재할당 횟수, 유휴시간 |
| 의사결정 품질 저하 | LLM이 복잡한 상황에서 잘못된 판단을 수행 | DAG 오류, 중복 작업, 부적절한 작업 할당 |

이 세 가지는 서로 관련되어 있지만 동일하지 않습니다.

예를 들어 에이전트 수가 증가하여 AC의 프롬프트가 길어졌다고 가정하겠습니다.

그 결과 API 응답시간이 늘어났다면 계산 오버헤드가 증가했다고 볼 수 있습니다.

하지만 응답시간은 그대로인데 AC가 동일한 작업을 여러 에이전트에게 중복 배정했다면 이는 의사결정 품질의 문제입니다.

**두 현상을 모두 'LLM 관리복잡도'라고 묶어버리면 실제 성능 저하의 원인을 식별하기 어려워집니다.**

### 3.2. 이 부분에서 OR이 구체적으로 어떤 역할을 할까요?

OR은 LLM의 스케줄링 결과를 비교·평가할 수 있는 기준을 제공할 수 있습니다.

예를 들어 다음과 같은 비교가 가능합니다.

| 조건 | 작업 할당 방식 | 연구 목적 |
| --- | --- | --- |
| A | 기존 LLM Agent Controller | Baseline |
| B | 규칙 기반 스케줄러 | 단순한 결정 규칙과 비교 |
| C | OR 기반 스케줄러 | 제약조건을 고려한 최적화와 비교 |

여기서 C를 반드시 구현해야 하는 것은 아닙니다.

초기 연구에서는 오히려 B만으로도 유의미한 결과를 얻을 가능성이 있습니다.

왜냐하면 다음과 같은 질문을 검증할 수 있기 때문입니다.

> 에이전트 수 증가에 따른 성능 저하가 실제로 복잡한 작업 할당 문제에서 발생하는가, 아니면 LLM을 통해 작업 할당을 수행하는 구조에서 발생하는가?

예를 들어 LLM 기반 할당에서는 에이전트 수가 증가할수록 성능이 떨어지지만, 동일한 환경의 규칙 기반 할당에서는 그러한 현상이 현저히 작게 나타난다고 가정하겠습니다.

이 경우 LLM 기반 관리 방식이 성능 저하에 기여한다는 가설을 뒷받침할 수 있습니다.

다만 이 실험만으로 LLM의 추론 복잡도 자체가 원인이라고 결론 내릴 수는 없습니다. 두 방식의 스케줄링 정책도 다르기 때문입니다.

이를 구분하려면 추가적인 통제 실험이 필요합니다.

## 4. RQ와 실험 지표를 명확히 정의하기

여기서는 현재 연구 문서의 한 가지 문제를 지적하고 싶습니다.

작성하신 연구 질문은 다음과 같습니다.

> 에이전트 수에 대해, 작업효율/에이전트당 효율의 저하의 원인은 무엇인가?

그런데 **작업효율과 에이전트당 효율은 서로 다른 지표**입니다.

이를 구분하지 않으면 나중에 결과를 해석할 때 문제가 생길 수 있습니다.

### 4.1. 기존 논문의 결과부터 살펴보겠습니다

원본 논문 Appendix A, Table 6에 제시된 수치를 가져오겠습니다.

| 에이전트 수 | 단순 작업 효율 E | 복잡한 작업 효율 E |
| ---: | ---: | ---: |
| 1 | 12.96 | 1.92 |
| 2 | 17.75 | 2.34 |
| 4 | 17.41 | 3.28 |
| 8 | 12.45 | 2.27 |

단위는 %/min이며, 원본 논문은 이를 Completion Rate / Execution Time으로 정의합니다. [ACL Anthology](https://aclanthology.org/2024.findings-acl.964.pdf?utm_source=chatgpt.com)

흥미롭게도 단순 작업에서는 2개 에이전트에서, 복잡한 작업에서는 4개 에이전트에서 가장 높은 효율이 관측됩니다.

그러나 이 수치만으로 자원 경쟁과 관리복잡도 중 무엇이 주원인인지 판단할 수는 없습니다.

또한 각 작업을 여섯 번 반복한 결과이므로, 효과 크기와 불확실성을 검토할 필요가 있습니다.

### 4.2. 연구에서는 효율을 두 차원으로 나누는 것이 좋겠습니다

첫 번째는 시스템 전체의 작업 효율입니다.

\[
E_{\text{system}}(n)=\frac{C(n)}{T(n)}
\]

- \(n\): 에이전트 수
- \(C(n)\): 작업 완료 비율
- \(T(n)\): 작업 수행 시간

두 번째는 에이전트당 효율입니다.

\[
E_{\text{agent}}(n)=\frac{C(n)}{nT(n)}
\]

이는 전체 성과를 에이전트 수로 정규화한 지표입니다. 에이전트별 실제 활동시간을 고려한 생산성 지표와는 다르다는 점에 주의해야 합니다.

여기서 중요한 사실이 있습니다.

**에이전트당 효율은 자원 경쟁이나 관리복잡도가 전혀 없어도 감소할 수 있습니다.**

예를 들어 작업의 병렬화 가능성이 낮다면 에이전트를 추가해도 전체 완료시간은 크게 줄어들지 않습니다.

이 경우 에이전트당 효율은 자연스럽게 감소합니다.

따라서 관측되는 성능 저하를 설명하기 위해서는 두 가설에 앞서 반드시 고려해야 할 요소가 있습니다.

### 가설 0: 작업 자체의 병렬화 가능성에 한계가 있다

이것은 OR의 그래프 기반 스케줄링과 연결되는 중요한 지점입니다.

전체 작업이 DAG로 표현된다고 가정하겠습니다.

작업 사이에 선후관계가 많다면 아무리 에이전트가 많아도 동시에 수행할 수 있는 작업 수에는 한계가 있습니다.

이론적으로, 작업시간이 알려져 있고 추가적인 자원 제약이 없다고 가정하면 다음과 같이 표현할 수 있습니다.

\[
T_n \geq \max\left(\frac{W}{n},L\right)
\]

여기서

- \(W\): 모든 작업의 총 처리시간
- \(n\): 에이전트 수
- \(L\): DAG의 임계경로 길이(Critical Path Length)

입니다.

즉, \(n\)이 무한히 증가하더라도 작업 수행시간은 임계경로 길이보다 짧아질 수 없습니다.

이는 머신러닝이나 LLM의 관리 능력과 무관하게 발생하는 구조적 한계입니다.

따라서 현재 연구에서 관측하는 현상을 최소한 다음 세 가지로 나누어 생각할 필요가 있습니다.

1. **작업의 구조적 병렬성 한계**
2. **공유자원에 대한 경쟁**
3. **LLM 기반 관리 오버헤드 및 의사결정 품질 저하**

개인적으로는 이 구분이 이번 논의에서 가장 중요한 발견이라고 생각합니다.

왜냐하면 가설 0을 고려하지 않으면 가설 1과 가설 2의 효과를 과대평가할 위험이 있기 때문입니다.

## 5. 실제로 세 원인을 어떻게 구분할 수 있을까요?

현재 연구의 현실적인 제약을 고려하면 처음부터 복잡한 OR 솔버를 개발할 필요는 없습니다.

대신 다음과 같은 비교 실험부터 시작할 수 있습니다.

| 실험 조건 | 작업 의존성 | 공유자원 경쟁 | LLM 기반 관리 |
| --- | --- | --- | --- |
| A | 낮음 | 낮음 | 사용 |
| B | 높음 | 낮음 | 사용 |
| C | 낮음 | 높음 | 사용 |
| D | 낮음 | 낮음 | 규칙 기반 |

각 조건에서 에이전트 수를 1, 2, 4, 8로 변경하는 것입니다.

물론 이러한 구성을 실제 VillagerBench에 구현할 수 있는지는 별도로 검토해야 합니다.

이 실험 설계에서 기대하는 해석은 다음과 같습니다.

- **A와 B의 비교**

작업의 의존성이 증가할수록 에이전트 추가에 따른 성능 향상이 제한되는지 확인합니다.

- **A와 C의 비교**

공유자원 경쟁이 심해지면 대기시간, 충돌, 작업 실패 등이 증가하는지 확인합니다.

- **A와 D의 비교**

LLM 기반 관리 구조가 성능에 어떤 영향을 미치는지 확인합니다.

다만 D는 스케줄링 정책도 변경하므로, 관리 오버헤드의 순수 효과를 식별하는 실험은 아닙니다.

이를 좀 더 엄밀하게 검토하려면 작업 배정 결과를 고정한 상태에서 LLM 호출·실행 비용을 분리하거나, 동일한 작업 할당을 서로 다른 실행 방식에서 재현하는 추가 실험이 필요합니다.

여기서 통계적 실험설계(Design of Experiments)가 중요한 역할을 합니다.

## 6. BA의 API 호출 최적화 제안에 대한 평가

이 부분은 연구 질문과 직접 연결되는 내용이므로 각각 평가하겠습니다.

### 6.1. 에이전트들이 반드시 병렬로 작업할 필요가 있는가?

**실행할 필요가 없는 작업을 병렬로 수행하도록 강제할 이유는 없습니다.**

원본 논문에서도 DAG를 활용해 병렬 실행과 순차 실행을 구분합니다.

다만 두 가지 상황을 구분해야 합니다.

**첫 번째는 작업의 논리적 병렬성입니다.**

작업 A와 B 사이에 의존성이 없다면 동시에 수행할 수 있습니다.

하지만 그것이 반드시 동시에 수행하는 것이 최적이라는 뜻은 아닙니다.

공유자원에 대한 경쟁 때문에 순차 실행이 더 효율적일 수 있습니다.

**두 번째는 실험 시스템의 실제 병렬성입니다.**

API 비용을 줄이기 위해 에이전트를 순차적으로 실행한다면, 원래 관측하려던 자원 경쟁이나 병렬화 효과가 사라질 수도 있습니다.

따라서 순차 실행을 도입하더라도 성능 비교에서 무엇을 측정하는지 명확해야 합니다.

특히 실제 경과시간(Wall-clock Time)을 비교하려면 순차 실행과 병렬 실행을 동일하게 취급할 수 없습니다.

### 6.2. BA의 외부 API를 로컬 LLM으로 교체하는 방안

연구비 절감과 실험 반복 가능성이라는 측면에서는 검토할 만한 방안입니다.

그러나 **외부 LLM을 로컬 LLM으로 교체하면 실험의 추론 성능 자체가 달라질 수 있다는 문제가 있습니다.**

예를 들어 기존 LLM보다 성능이 낮은 로컬 모델을 사용하면 작업 실패가 증가할 수 있습니다.

이때 관측된 효율 저하가 관리복잡도 때문인지, 모델 능력 차이 때문인지 구분하기 어렵습니다.

반대로 로컬 모델에서 추론 지연이 증가해 성능이 저하될 수도 있습니다.

따라서 다음과 같이 구분하는 편이 좋겠습니다.

- **기준 실험:** 동일한 LLM 모델과 설정을 유지해 원본 결과의 재현성을 확인
- **비용 절감 실험:** 로컬 LLM을 사용하되 별도의 실험 조건으로 구분

또한 로컬 LLM에서는 동시 요청 증가에 따른 GPU 메모리와 추론 처리량의 제약이 새롭게 발생할 수 있습니다.

이 역시 연구에서 측정하려는 자원 경쟁과 혼동되지 않도록 주의해야 합니다.

### 6.3. 각 에이전트의 대화 로그를 JSON으로 기록하는 방안

세 제안 중에서는 **가장 먼저 추진할 가치가 높은 작업**입니다.

다만 대화 내용만 저장하는 것으로는 부족합니다.

연구 질문을 검증하려면 최소한 다음 데이터를 기록하는 것이 좋겠습니다.

| 로그 유형 | 기록 내용 |
| --- | --- |
| Agent | ID, 할당 작업, 작업 시작 및 종료 시각 |
| Task | 작업 ID, 선행 작업, 실행 상태 |
| LLM | 호출 목적, 입력·출력 토큰 수, 응답 지연 |
| Scheduling | 작업 할당, 재할당, 대기시간 |
| Environment | 자원 접근, 이동 실패, 작업 충돌 |
| Result | 성공·실패, 완료시간, 오류 유형 |

이때 모든 로그에 공통적인 `run_id`, `task_id`, `agent_id`, 타임스탬프 등을 부여해야 합니다.

특히 에이전트의 대기시간을 다음과 같이 분류할 수 있다면 유용합니다.

$$
T_{\text{waiting}}
=

T_{\text{dependency}}
+
T_{\text{resource}}
+
T_{\text{coordination}}
+\cdots
$$

이는 대기 원인을 구분하기 위한 개념적 분해이며, 실제 로그에서는 대기 사유가 중첩될 수 있으므로 중복 계산을 피하는 규칙이 필요합니다.

그리고 한 가지 더 중요합니다.

**실험 로그 보존과 에이전트의 컨텍스트 보존은 별도의 문제입니다.**

JSON에 대화를 기록하는 것만으로 다음 LLM 호출에서 컨텍스트가 자동으로 유지되지는 않습니다.

저장한 데이터를 어떤 방식으로 읽어 프롬프트에 포함할지, 요약할지, 검색할지도 별도로 설계해야 합니다.

원본 VillagerAgent의 State Manager가 이미 에이전트 상태와 작업 이력을 관리한다는 점도 고려해야 합니다. [ACL Anthology](https://aclanthology.org/2024.findings-acl.964.pdf?utm_source=chatgpt.com)

따라서 기존 상태 관리 구조를 파악한 뒤 관측용 로깅을 확장하는 것이 합리적입니다.

## 7. 이번 랩미팅에서 우선적으로 다룰 연구 방향

여기서는 앞서 사용자님이 강조하셨던 **탐색 범위를 무분별하게 확장하지 않는다는 원칙**에 동의합니다.

OR이라는 새로운 분야를 발견했다고 해서 지금 당장 조합최적화, 그래프 신경망, 강화학습, 확률최적화까지 공부할 필요는 없습니다.

현재 연구 질문을 기준으로 필요한 개념을 선별한다면 다음 정도가 적절하겠습니다.

| 개념 | 우선순위 | 이유 |
| --- | --- | --- |
| DAG 및 Critical Path | 높음 | 병렬화 가능성과 구조적 병목 파악 |
| Resource-Constrained Scheduling | 높음 | 공유자원 경쟁과 작업 할당 문제 분석 |
| OS Synchronization / Contention | 높음 | 자원 충돌과 대기 현상 이해 |
| 실험설계 및 인과적 식별 | 높음 | 효율 저하의 원인 구분 |
| Queueing Theory | 중간 | API·추론 대기 및 처리량 분석 |
| 정수계획법(MILP) | 중간 | 비교 기준 스케줄러를 개발할 경우 |
| GNN / Deep RL | 낮음 | 현재 RQ의 원인 분석에 필수적이지 않음 |

AOS, CRLS, ITA와 같은 탐색 후보 역시 지금 단계에서는 보류해도 무방하겠습니다. 해당 기법들이 무엇을 해결하며 VillagerAgent의 어떤 병목에 대응하는지가 먼저 명확해져야 하기 때문입니다.

### 연구 질문을 조금 더 정교하게 표현한다면

현재 RQ:

> 에이전트 수에 대해, 작업효율/에이전트당 효율의 저하의 원인은 무엇인가?

다음과 같이 정리하는 것을 제안합니다.

**RQ: What factors contribute to the degradation of task execution efficiency as the number of LLM-based agents increases in VillagerAgent?**

이를 세 가지 하위 질문으로 분해할 수 있습니다.

- **RQ1:** 작업 의존성과 제한된 병렬성이 에이전트 확장성에 어느 정도 영향을 미치는가?
- **RQ2:** 공유자원 경쟁이 작업 효율 저하에 어느 정도 기여하는가?
- **RQ3:** LLM 기반 작업 관리의 계산 오버헤드와 의사결정 품질 저하가 작업 효율에 어떤 영향을 미치는가?

여기서 세 질문이 반드시 상호배타적일 필요는 없습니다. 실제 시스템에서는 세 요인의 상호작용도 존재할 수 있습니다.

## 8. 종합 평가

현재 문서에서 긍정적으로 평가할 부분은 **해결 알고리즘을 먼저 정하지 않고, 관측된 현상의 원인을 규명하려는 연구 질문을 설정했다는 점**입니다.

특히 원본 논문 Table 6에는 에이전트 수에 따른 비단조적인 성능 변화가 실제로 관측되어 있습니다. 이를 출발점으로 삼을 수 있습니다.

다만 다음 세 가지는 보완하는 편이 좋겠습니다.

첫째, 효율 저하를 설명할 때 병렬화의 구조적 한계를 반드시 고려해야 합니다.

둘째, 자원 경쟁과 LLM 관리복잡도를 실제로 구분해 관측할 수 있도록 로깅과 실험 조건을 설계해야 합니다.

셋째, API 비용 절감을 위한 시스템 수정이 연구 결과에 영향을 주지 않도록 기준 실험과 최적화 실험을 구분해야 합니다.

**그리고 OR과 관련해서는 지금 당장 새로운 스케줄링 알고리즘을 개발하기보다, DAG의 구조적 병렬성 및 RCPSP 관점에서 VillagerAgent의 기존 스케줄러가 얼마나 효율적으로 자원을 활용하는지를 분석하는 것이 더 자연스러운 첫 단계**라고 판단합니다.

특히 다음 질문은 별도로 검토할 가치가 있습니다.

> **에이전트 수가 증가할 때 실제로 작업의 병렬 실행 능력이 부족해서 성능이 떨어지는 것인가, 아니면 병렬 실행이 가능한 작업이 존재함에도 VillagerAgent가 이를 효율적으로 할당하고 실행하지 못하는 것인가?**

두 현상은 관측 결과가 비슷해도 원인과 해결 방법이 완전히 다릅니다.

전자는 작업 그래프의 구조적 특성에 가까운 문제이고, 후자는 스케줄링 및 에이전트 관리 정책의 문제입니다.

이 구분을 명확히 한다면 OR은 단순히 새로운 참고 분야를 하나 추가하는 것이 아니라, **현재 연구 질문의 가설 구성과 실험설계를 개선하는 직접적인 방법론**이 될 수 있습니다.
